# Design

`ucrc` is a C11 library that computes CRC-8, CRC-16 and CRC-32 over a stream of octets. One engine serves every width: the model is data passed at run time, and the computation strategy is a compile-time choice. It allocates nothing and keeps no mutable state.

## Goals and non-goals

Goals:

- Any CRC up to 32 bits from one descriptor type, including application-defined models.
- A size and speed trade-off chosen once per build, with tables in read-only memory.
- Results that do not depend on the target's byte width.
- Defined behaviour on contract violations when assertions are compiled out.

Non-goals:

- CRCs wider than 32 bits, or widths other than 8, 16 and 32.
- Hardware CRC peripherals. The engines are portable software.
- Integrity against deliberate tampering. A CRC is not a cryptographic check.

## Models

`ucrc_model_t` carries the standard CRC parameters: `width`, `poly`, `init`, `refin`, `refout` and `xorout`. These are the parameters published for each named CRC in catalogues such as CRC RevEng, so a model is written down by copying its catalogue entry. The register is a `uint32_t` for every width, and every result is masked to the width, so one set of functions serves all three widths without per-width types or casts.

The model's `table` field selects the engine per call. `NULL` selects the bitwise engine, which supports every combination of parameters. A table selects the table engine for the build's strategy. The predefined models are `const` objects whose `table` matches the strategy, so they take the fast path and an application-defined model takes the bitwise path in the same image.

## Strategies

| Strategy | Table per predefined width | Work per octet |
| --- | --- | --- |
| `UCRC_STRATEGY_BITWISE` | none | 8 shift-and-XOR steps |
| `UCRC_STRATEGY_NIBBLE` | 16 entries, 64 bytes | 2 lookups |
| `UCRC_STRATEGY_BYTE` | 256 entries, 1 KiB | 1 lookup |

Table entries are `uint32_t` for every width, which costs CRC-8 and CRC-16 some ROM but lets one table engine serve all widths. Tables are `static const`, so they are placed in flash or `.rodata` and cost no RAM. The bitwise engine is always compiled, because it serves application-defined models in every strategy.

Only enabled widths produce tables and model objects. A build that needs only CRC-32 with the byte strategy carries one 1 KiB table.

### Table engines and reflection

A reflected table model keeps its running register reflected and shifts it right, which removes the per-octet reflection. A non-reflected model keeps the register in normal form and shifts it left. `ucrc_finish` reflects the register once when `refout` differs from the form it was kept in, so table models handle `refin != refout` at the cost of one reflection per message. The bitwise engine instead reflects each input octet when `refin` is set and keeps the register in normal form, so it handles `refin != refout`.

Because of this, the running value between `ucrc_begin` and `ucrc_finish` is opaque: its bit order depends on the engine. `ucrc_finish` applies the remaining reflection and `xorout`, so the final result is the same for every strategy.

### Generated tables

`src/ucrc_tables.c` is generated by `tools/gen_tables.c` and committed, so a build needs no code generation and a cross build needs no host tool. The generator builds with the host compiler, `meson compile regen-tables` rewrites the file, and the `tables-up-to-date` test fails when the committed file differs from the generator's output.

## Streaming

The running value is returned to the caller and passed back in, rather than held in a context object or a static. The library therefore has no state to protect, any number of streams can be open at once, and an interrupt handler can compute a CRC while a task is mid-stream. Folding octets is associative over chunk boundaries, so `ucrc_update` may be called with any split of the input, including empty chunks.

## Octets on wide-byte targets

A CRC is defined over 8-bit octets. Where `CHAR_BIT` is 16, the smallest object is 16 bits and `uint8_t` does not exist, so `ucrc_platform.h` defines `ucrc_octet_t` as `uint16_t` there and as `uint8_t` elsewhere. Every engine reads only the low 8 bits of each element and `len` counts elements, so the same octet stream gives the same CRC on both kinds of target. The library does not unpack two octets from one word, because it cannot know the packing order; the caller splits packed words first.

`UCRC_SIMULATE_16BIT_MAU` forces the 16-bit octet type on a byte-addressed host, so the test suite exercises this path without target hardware.

## Contract checks

Preconditions are checked with `UCRC_ASSERT`, which defaults to `assert` and can be redefined to call a supervisor. The checks are followed by defensive returns, so a build with assertions compiled out still never dereferences a `NULL` model or buffer: `ucrc_begin`, `ucrc_finish` and `ucrc_compute` return `0`, and `ucrc_update` returns its input register. The model's `width` and `table` are trusted and not checked at run time; a model is normally a `const` object written once and reviewed.

## Portability

- C11 with `<stdint.h>`, `<stdbool.h>`, `<stddef.h>`, `<limits.h>`, and `<assert.h>` for the default `UCRC_ASSERT`. No other dependencies.
- No `uint8_t` where `CHAR_BIT` is 16.
- Every shift is by less than the width of a `uint32_t`, and all arithmetic is unsigned.
- A static assertion rejects an addressable unit other than 8 or 16 bits.

## Verification

The test suite is built once per strategy, once with the 16-bit-MAU simulation, and once with assertions compiled out. Each build checks:

- the predefined models against their published check values, and an application-defined CRC-16/MODBUS model through the bitwise path;
- every single-octet input and 4000 random buffers against an independent reference engine, plus large buffers;
- streaming against one-shot results for every chunk boundary and for random boundaries, including empty chunks;
- width masking, detection of every single-bit error, and the CRC residue of a message followed by its own CRC;
- the empty message and the defensive returns for `NULL` arguments.

When zlib is available, a further test compares CRC-32/ISO-HDLC with zlib's `crc32()`. CI runs the suite under AddressSanitizer and UndefinedBehaviorSanitizer, compiles every strategy with each width enabled alone and all together with warnings as errors, and gates `src/` and `include/` at 100 percent line and branch coverage. A documentation test compiles every C example in the README and `docs/` against the header.

CI compiles the library with warnings as errors under TI C2000 Code Generation Tools 22.6.2.LTS and 25.11.1.LTS in C11 C28x mode, under both the COFF and EABI ABIs, and for an Arm Cortex-M0 with freestanding flags. This validates the source dialect and type assumptions only. Linking, target execution, and final map-file footprint remain consumer-owned checks.

MISRA C:2023 analysis with `misch` runs in CI and fails on any finding not covered by the deviations recorded in `misra-deviations.txt` and inline in `src/ucrc.c` and `include/ucrc.h`. The inline deviation in the header is Rule 2.5 (unused macro) for the version macros, which exist for consumers and are not used by the library.
