# Contributing to ucrc

ucrc is a small, dependency-free CRC-8/16/32 library used as an integrity primitive for embedded firmware, RTOS, and Linux targets. It is designed to be safe to drop into audited and safety-relevant codebases, so contributions are held to that bar.

## Getting started

The same commands CI runs, locally:

```sh
# Configure with tests + sanitisers (CI default). The suite builds every
# strategy (bitwise / nibble / byte), the 16-bit-MAU simulation, and an
# assertions-disabled variant.
meson setup build --buildtype=debug -Dbuild_tests=true \
                  -Db_sanitize=address,undefined
meson compile -C build
meson test -C build --verbose

# Coverage (CI gate is 80% line + 70% branch)
meson setup build_cov --buildtype=debug -Dbuild_tests=true -Db_coverage=true
meson compile -C build_cov && meson test -C build_cov
gcovr --root . --filter 'src/' --filter 'include/' --print-summary
```

## Source style

- `.clang-format` is mandatory. Run `clang-format -i` on every modified `.c` / `.h` file before submitting. CI enforces it.
- 8-space indent, Linux brace style, 80-column limit. Match the existing conventions; do not reformat unrelated code.
- Do **not** run `clang-format` on `src/ucrc_tables.c`. It is generated, carries its own `clang-format off` guard, and the freshness test compares exact bytes.
- Meson is the single source of truth for the build. Update `meson.build` / `tests/meson.build` when adding or removing source files. No CMake, no Make, no other build systems.

## C language rules

- C11 only (uses `_Static_assert`).
- Use fixed-width types from `<stdint.h>` and `<stdbool.h>`. Never plain `int` for values that must be a specific width.
- No heap allocation (`malloc`, `free`, VLAs), no recursion, no global mutable state.
- Public functions must never invoke undefined behaviour on bad arguments: guard pointers, treat `len == 0` as a no-op, and report contract violations through `UCRC_ASSERT` (which an integrator may redirect to a safety handler).
- A build with `UCRC_ASSERT` disabled must still be defined behaviour for every input.

## Generated tables

- `src/ucrc_tables.c` is generated by `tools/gen_tables.c` and committed. Do not hand-edit it.
- To change the predefined model list or the table maths, edit the generator, then regenerate: configure with `-Dbuild_tests=true` and run `meson compile regen-tables`.
- The generator output must stay deterministic (no timestamps, stable ordering). The `tables-up-to-date` test fails if the committed file is stale.
- The file is committed on purpose: copy-in consumers and non-Meson build systems do not run Meson, and a cross build cannot run a build-time generator. Do not convert it to a build-time `custom_target`.

## Strategy and width matrix

- `UCRC_STRATEGY` (bitwise / nibble / byte) is a compile-time choice that selects one engine. The bitwise engine is **always** compiled as the fallback for models whose `table` is `NULL`; keep it that way.
- A change to the engine must pass every strategy, the 16-bit-MAU simulation, and every width-enable combination.
- On 16-bit-MAU targets only the low 8 bits of each `ucrc_octet_t` are used. Always mask octets and table indices with `& 0xFFu` (or `& 0xFu` for nibbles).

## Tests and coverage

- Add a test for every bug fix and every new feature.
- Any new CRC behaviour must be checked against a published `check` constant or the independent reference engine (`ucrc_test_ref`), never against ucrc alone.
- In test code, never use `sizeof(array)` as an element count: `ucrc_octet_t` is `uint16_t` under the 16-bit-MAU simulation, so `sizeof` is twice the count. Use an explicit length.
- Fuzz seeds are fixed so failures reproduce from the test name alone. Do not introduce non-deterministic tests.
- CI enforces an 80% line / 70% branch coverage gate. New code without tests will fail it.

## MISRA C:2023

ucrc is written to be MISRA C:2023 aware: fixed-width unsigned types, explicit `u` suffixes, no heap, no recursion, no `errno`, `static const` tables, and no undefined-behaviour shifts. The deviation record lives in the file header of `src/ucrc.c`. If your change introduces a new deviation, add an entry there (rule, sites, justification) and flag it in the pull-request description. Full tool-driven compliance requires running a certified static analyser against the source; this repository does not vendor one.

## Commits

Use Conventional Commits:

- `feat: ...` new feature
- `fix: ...` bug fix
- `doc: ...` documentation only
- `test: ...` test-only changes
- `chore: ...` build, CI, release work
- `refactor: ...` code change that neither fixes a bug nor adds a feature

Keep the subject under ~70 characters. Use the body to explain _why_ the change is needed, not _what_ the diff already shows.

## Pull requests

- Open an issue first for non-trivial changes so the design can be agreed before implementation.
- Keep PRs focused: one feature or one fix per PR.
- All CI checks must pass: tests on Linux and macOS under ASan+UBSan, the release build, the coverage gate, the format check, the docs build, and the cross-compile smoke.
- Flag any new MISRA deviation in the PR description.

## When in doubt

Open an issue and discuss before writing code. The library is small enough that even modest design changes have outsized implications for the consumers that depend on its wire-compatible CRC values.
