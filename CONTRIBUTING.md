# Contributing to ucrc

`ucrc` is a small C11 library that computes CRC-8, CRC-16 and CRC-32 over octet streams. Its results are wire-compatible values that other systems check, so two contracts carry most of the design weight: every strategy gives the published result for every model, and no input, however invalid, causes undefined behaviour. Keep both in mind when you change anything.

## Getting started

Install a C11 compiler and install the Python tools with [uv](https://docs.astral.sh/uv/), as CI does. The MISRA analysis also needs a current `cppcheck`; CI installs it from Homebrew because the 2.13 release in Ubuntu 24.04 reports different findings. The same commands CI runs, locally:

```sh
# Python tools
uv tool install meson
uv tool install ninja
uv tool install gcovr
uv tool install misch

# Configure with tests and sanitisers (CI default). The suite builds every
# strategy, the 16-bit-MAU simulation, and an assertion-recording variant.
meson setup build --buildtype=debug -Dbuild_tests=true -Db_sanitize=address,undefined
meson compile -C build
meson test -C build --verbose

# Coverage (CI gate is 100% line and branch for src/ and include/)
meson setup build_cov --buildtype=debug -Dbuild_tests=true -Db_coverage=true
meson compile -C build_cov && meson test -C build_cov
gcovr --root . --filter 'src/' --filter 'include/' --merge-mode-functions=separate --print-summary

# MISRA C:2023 (reads build/compile_commands.json)
misch run

# Formatting (pinned clang-format through uvx)
scripts/format.sh --fix
```

## Source style

- Formatting is mandatory. Run `scripts/format.sh --fix` before submitting, or `scripts/format.sh` to check without writing, as CI does. The script pins the clang-format release and runs it through `uvx`, so an editor formatter gives the same result only when it runs the same release.
- `src/ucrc_tables.c` is generated and wrapped in a `clang-format off` guard, so the formatter leaves it byte-for-byte unchanged. Never format it by other means.
- 8-space indent, Linux brace style, 80-column limit. Match the existing conventions and do not reformat unrelated code.
- The Meson build system is the single source of truth. Update `meson.build` and `tests/meson.build` when you add or remove files. No CMake, no Make, and no other build systems.

## C language rules

- C11 only.
- Use fixed-width types from `<stdint.h>` and `<stdbool.h>`. Do not use `uint8_t` outside `ucrc_platform.h`; octets are `ucrc_octet_t`.
- No heap allocation (`malloc`, `free`, VLAs), no recursion, and no global mutable state.
- Public functions never invoke undefined behaviour on bad arguments: guard pointers, treat `len == 0` as a no-op, and report contract violations through `UCRC_ASSERT`. A build with `UCRC_ASSERT` compiled out must still be defined for every input.
- Mask every octet with `& 0xFFu` and every table index with `& 0xFFu` or `& 0xFu`, so only the low 8 bits of a `ucrc_octet_t` are used where `CHAR_BIT` is 16.

## Generated tables

- `src/ucrc_tables.c` is generated by `tools/gen_tables.c` and committed. Do not edit it by hand.
- To change a predefined model or the table maths, edit the generator, then run `meson compile -C build regen-tables`.
- Keep the generator output deterministic: no timestamps and a stable order. The `tables-up-to-date` test fails when the committed file is stale.
- The file is committed because copy-in consumers and other build systems do not run Meson, and a cross build cannot run a target-built generator. Do not turn it into a build-time `custom_target`.

## Strategies and widths

- `UCRC_STRATEGY` selects one table engine at compile time. The bitwise engine is always compiled, because it serves every model whose `table` is `NULL`; keep it that way.
- An engine change must pass every strategy, the 16-bit-MAU simulation, and every width-enable combination. CI builds each strategy with each width alone and with all three.

## MISRA C:2023

The library is analysed with `misch` (cppcheck-backed MISRA C:2023 analysis), configured by `misra.toml`, over `src/` and `include/`. It reads the compilation database from a Meson `build/` directory, so configure one first. CI fails on any finding not covered by `misra-deviations.txt` or an inline suppression.

A change must not add findings. If one is unavoidable, record a deviation with its rule, sites and justification, both in `misra-deviations.txt` or an inline `cppcheck-suppress` comment and in the deviation record in the header of `src/ucrc.c`, and flag it in the pull request.

Full tool-driven compliance beyond this analysis needs a certified static analyser, which this repository does not vendor.

## Tests and coverage

- Add a test for every bug fix and every new behaviour.
- Check new CRC behaviour against a published check value or the independent reference engine `ucrc_test_ref`, never against `ucrc` alone.
- The suite has a shared harness (`tests/test_harness.c`), shared fixtures and the reference engine (`tests/test_support.c`), and one module per category. Each module exposes a `run_<category>_tests()` called from `tests/test_main.c`; register new files in `tests/meson.build`.
- Never use `sizeof(array)` as an element count in tests: `ucrc_octet_t` is 16 bits under the 16-bit-MAU simulation, so `sizeof` is twice the count.
- Fuzz seeds are fixed so a failure reproduces from the test name. Do not add non-deterministic tests.
- CI enforces 100 percent line and branch coverage of `src/` and `include/`.
- The `ucrc docs examples` test compiles every C code block in `README.md`, `CONTRIBUTING.md`, and `docs/` against the public header, through `tests/docs/check_snippets.py`. A block compiles at file scope by default. On the line directly above the fence, put `<!-- snippet: body -->` for a block of statements, or `<!-- snippet: skip -->` for pseudo-code or a copy of a header definition.

## Documentation

| File | Purpose |
| --- | --- |
| `README.md` | Landing page: quick start, description, validated toolchains, and links. Keep it short. |
| `docs/integration.md` | Installation, configuration, building, and cross builds. |
| `docs/api.md` | Reference for every function and predefined model. |
| `docs/design.md` | Models, strategies, tables, octets on wide-byte targets, contract checks, and verification. |

Update `docs/api.md` and the header Doxygen together when an interface changes. Update `docs/design.md` when behaviour changes. Keep it standalone: describe how the library works, not how it was built or which other projects use it. Write prose in British English, one line per paragraph.

## Commits

Use Conventional Commits:

- `feat: ...` new feature
- `fix: ...` bug fix
- `docs: ...` documentation only
- `test: ...` test-only changes
- `chore: ...` build, CI, release work
- `refactor: ...` a change that neither fixes a bug nor adds a feature

Keep the subject under about 70 characters. Use the body to explain why the change is needed.

## Pull requests

- Open an issue first for non-trivial changes so the design can be agreed before implementation.
- Keep pull requests focused: one feature or one fix.
- All CI checks must pass.
- Flag any new MISRA deviation in the description.

## When in doubt

Open an issue. A change to a CRC result breaks every peer that checks it.
